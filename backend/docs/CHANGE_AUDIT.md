# บันทึกการแก้ไข — 17 กันยายน 2569

แก้จากผลตรวจวันที่ 16 กันยายน โดยเน้นความถูกต้องของทะเบียนและการใช้งานเว็บปัจจุบัน

| ส่วน | ผลการแก้ไข |
| --- | --- |
| เปิดเว็บในเครื่อง | Next.js อ่าน root .env โดยไม่ทับ environment ของผู้ให้บริการ |
| ติดตั้งฐานข้อมูล | เพิ่ม db:deploy/db:status และ migration เริ่มต้น; runtime ตรวจตารางแบบอ่านอย่างเดียว |
| Seed | คืน exit code ล้มเหลวจริงและปิด Prisma/pg pool โดยไม่บังคับ exit 0 |
| คำขอพร้อมกัน | ใช้ Serializable กับ mutation เพื่อให้ version/pending check และการบันทึกอยู่ใน transaction เดียวกัน |
| Batch import | validate ก่อนบันทึก ไม่เดาจำนวน/เงิน ไม่เติมรหัสซ้ำอัตโนมัติ และ rollback ทั้ง assets กับ source decisions เมื่อขัดแย้ง |
| สาขา | แยก วคม/วค และ ควอ/วอ ให้ถูกต้อง ให้ค่าสาขาชัดเจนสำคัญกว่าหมายเหตุ และรักษารหัสที่ยังไม่ทราบความหมาย |
| รหัสต้นฉบับซ้ำ | ตรวจรหัสที่ไม่มีตัวเลขด้วย พบเพิ่ม 2 แถวที่ต้องตรวจทาน จึงเหลือ 1,194 แถวพร้อมนำเข้า |
| Excel/พิมพ์ | ใช้ยอด totalSatang ตามทะเบียนและวันที่รายงานปัจจุบัน |
| ตรวจนับ | ฟอร์มรักษาผลเดิม การเปลี่ยนรอบไม่ใช้รายการจากรอบก่อน |
| ค่าซ่อม | เก็บประมาณการค่าซ่อมในคำขอและแสดงให้ผู้อนุมัติ |
| Session/UI | ล้าง workspace และยกเลิกคำขอค้างเมื่อ session สิ้นสุด ไม่รับ response จากบัญชีเดิม |
| นำเข้าบน UI | ไม่ใช้ source เก่าขณะเปลี่ยนไฟล์/โหลดไม่สำเร็จ รักษาโฟกัสช่องค้นหาระหว่างโหลด จำกัดเลือกกลุ่มเฉพาะรายการพร้อม และใช้เพดาน 4 MB ตรงกับ backend |
| หน้า login | เอาค่าบัญชี/รหัสผ่านกรอกล่วงหน้าและข้อความสร้าง Admin อัตโนมัติที่ไม่ตรงกับระบบออก |
| ข้อผิดพลาด | ไม่คืนรายละเอียด exception ภายในผ่าน API; เอารหัสเชื่อม DB ที่เขียนตายตัวออกจากสคริปต์ส่งออก |

การแก้ชื่อห้อง/สาขาที่บันทึกผิดยังทำได้พร้อมเหตุผลและ audit ตามพฤติกรรม UI เดิม ปรับ test เก่าที่คาดว่าจะห้ามแก้ให้สอดคล้องกัน การโอนย้ายจริงยังมีคำขอและสายอนุมัติ

## หลักฐานการทดสอบ

- `npm test`: ชื่อสาขา, ยอด Excel หลังเขียน/อ่าน XLSX, รหัสซ้ำไม่มีตัวเลข และการยกเลิก request จาก session เดิม
- `npm run test:domain`: จำนวนเงิน/แบ่งล็อต/รหัสช่วง/ต้นฉบับ 4,312 แถว/ค่าเสื่อม
- `npm run typecheck` และ `npm run build`
- `npm run test:integration`: สร้าง PostgreSQL database ใหม่ชื่อสุ่มบน server ทดสอบ loopback แล้วติดตั้ง migration, seed และเปิด production build เพื่อทดสอบผู้ใช้ 5 บทบาท, cookies/CSRF, idempotency, คำขอชนกัน, สายอนุมัติ, แบ่งล็อต, batch rollback/replay, rollback ทั้งแม่/ลูก/การตัดสินใจเมื่อรหัสลูกของช่วงซ้ำ, ค่าซ่อม, ตรวจนับ, upload/download และ session revocation
- นำเข้าต้นฉบับจริงเฉพาะแถวพร้อม 1,194 รายการในฐานข้อมูลทดสอบ ตรวจว่าจำนวนและยอดรวมตรงทุกสตางค์
- ลอง UI จริง: login, เพิ่มครุภัณฑ์ที่ยอดต่างจากผลคูณพร้อมเหตุผล, เปิดรอบตรวจนับ, บันทึกชำรุด, เปิดแก้เฉพาะหมายเหตุและยืนยันผลเดิมยังเป็นชำรุด
- ทดสอบ session หมดอายุขณะเปิดทะเบียนใน browser: เมื่อรีเฟรชทะเบียน ข้อมูลหายจาก workspace และกลับหน้า login พร้อมข้อความแจ้งหมดเวลา
- ทดสอบการตั้งค่าฐานข้อมูลเดิมผ่าน localhost: readiness/login/read registry/logout สำเร็จ อ่านทะเบียนเดิม 125 รายการ โดยไม่แก้ข้อมูลครุภัณฑ์

ดูวิธีรันและข้อกำหนดที่ [UPGRADE.md](UPGRADE.md) ข้อมูลที่สร้างจาก tests อยู่ในฐานข้อมูลทดสอบแยก ไม่รวมกับทะเบียนเดิม

## ตรวจเพิ่มเติม — 23 กันยายน 2569

- บัญชีที่ผู้ใช้ให้มาทั้ง 5 บทบาท login/read registry/read source/logout ได้สำเร็จ ไม่เก็บรหัสผ่านในไฟล์โปรเจค
- ตรวจสิทธิ์ด้วยคำขอข้อมูลไม่ครบที่บันทึกไม่ได้ 20 กรณี: user/workflow/create/upload คืน 400 หรือ 403 ตามบทบาท และข้อมูลทะเบียน คำขอ รอบตรวจนับ ไฟล์ต้นฉบับ และ audit ไม่เปลี่ยน
- users/invites แสดงเฉพาะ Admin และไม่พบ passwordHash/tokenHash ในข้อมูล API
- เพิ่มรีเฟรชข้อมูลทุกหน้า อัปเดตเมื่อสลับเมนูหรือกลับมาโฟกัสหน้าต่าง เพื่อให้ผู้อนุมัติเห็นข้อมูลล่าสุด และให้รายการตรวจนับโหลดตามข้อมูลที่รีเฟรช
- แก้ชื่อบทบาท/สายอนุมัติเป็น “รองฝ่ายบริหาร” ให้ตรงกับบัญชีและหน้าที่ที่ผู้ใช้ระบุ
- ประวัติครุภัณฑ์แสดงเฉพาะรายการ/รุ่นข้อมูลที่เลือก ไม่รับ response เก่าหลังสลับรายการหรือปิดหน้า; เพิ่มสถานะกำลังโหลดและข้อความเมื่อโหลดไม่สำเร็จ
- ทดสอบหน้าเจ้าหน้าที่จริง: เมนูและปุ่มตามสิทธิ์ ค้นหาต้นฉบับโดยพิมพ์ K แล้ว SU หลังโหลดเสร็จได้ค่า KSU และโฟกัสอยู่ที่ช่องเดิม
- ทดสอบบัญชี Head บนเว็บจริง: ไม่มีปุ่มเพิ่มครุภัณฑ์/จัดการผู้ใช้ หน้าอนุมัติโหลดเมื่อเข้าเมนูและมีปุ่มรีเฟรชโดยไม่ต้องออกไปหน้าทะเบียน
- Typecheck และ unit tests ผ่าน; ทดสอบลำดับ response ประวัติด้วยข้อมูลจำลอง รวมการสลับรายการ การเปลี่ยน version การโหลดล้มเหลว และ unmount ผ่าน

## เพิ่มรูปครุภัณฑ์ — 24 กันยายน 2569

- รูปย่อในตารางและรูปเต็มในรายละเอียด พร้อมเลือกไฟล์/ดูตัวอย่าง/บันทึก/เปลี่ยน/ลบรูป; ไม่มีรูปใช้ช่องว่างที่สื่อความหมาย ไม่ใส่รูปตัวอย่างแทนครุภัณฑ์จริง
- ใช้ `stored_files` เดิม คีย์ `asset-images/<assetId>.webp`; ไม่เปลี่ยน schema ของฐานข้อมูลเดิม
- API `/api/asset-image` ตรวจ session ทุกครั้ง อนุญาต staff/admin แก้รูป และทุกบทบาทดูรูปหลังเข้าสู่ระบบ
- ตรวจไฟล์ด้วย decoder จริง จำกัด 4 MB/25 ล้านพิกเซล ปฏิเสธ SVG/ภาพเคลื่อนไหว ย่อเป็น WebP ไม่เกิน 1,600 พิกเซลและตัด EXIF/GPS
- ป้องกันการทับรูปใหม่ด้วย expectedVersion และ Serializable transaction บันทึก audit เฉพาะข้อมูลรูป ไม่เก็บ binary ลง JSON และไม่เปลี่ยน Asset.version/ยอดเงิน/จำนวน
- การอ่านและการบันทึกรูปถูกยกเลิกเมื่อสลับรายการหรือออกจากระบบ; URL ตัวอย่างใน browser ถูกคืนหน่วยความจำเมื่อเลิกใช้
- ผ่าน unit tests 10 กรณี, typecheck, production build และ integration เดิมพร้อมชุดรูปภาพ: สิทธิ์ 5 บทบาท/CSRF/ไฟล์เสียและปลอมชนิด/ขนาดคำขอแบบไม่มี Content-Length/อัปโหลดและลบ/เปลี่ยนรูปพร้อมกัน/ไม่เปลี่ยนยอดเงินและ Asset.version
- ลอง browser บนฐานทดสอบ: เลือก PNG ผ่าน file chooser, ดูตัวอย่าง, บันทึก, เห็นรูปเต็มและรูปย่อ จากนั้นรีโหลดเว็บแล้วยังโหลดรูปจริงได้ครบ 640×480
- เว็บ localhost เชื่อมฐานข้อมูลเดิมได้หลังอัปเกรด อ่านได้ 125 รายการ รูปจริงยัง 0 รายการ ไม่อัปโหลดรูปทดสอบลงทะเบียนเดิมและไม่เปลี่ยน schema
- เพิ่ม sharp เป็น dependency โดยตรง; npm ปรับ lockfile ให้ตรง package.json ปัจจุบัน (ตัด dependencies ของระบบเก่าที่ไม่อยู่ใน manifest เดิมแล้ว)

## แก้จากการตรวจเพิ่มเติม — 27 กันยายน 2569

- การคำนวณเงินในฟอร์มใช้ตัวแปลงเดียวกับการบันทึกและคำนวณเป็นสตางค์ด้วย BigInt รองรับ comma และราคา 0
- การจำแนกแถวต้นฉบับไม่ใช้คำในหมายเหตุเพื่อตัดสินว่าเป็นหัวตาราง/ยอดรวม และอ่านสาขา/หมวด/สำนักงานตามหัวตารางของรูปแบบ 10 และ 11 คอลัมน์
- ต้นฉบับยังครบ 4,312 แถว พร้อมนำเข้า 1,194 รายการ จำนวนแถวที่อาจเป็นครุภัณฑ์ลดลงหนึ่งแถว เพราะแก้ `วิทยาศาสตร์:36` ซึ่งเป็นยอดรวมจริงที่เคยถูกจัดผิด
- อ่านและจำแนกต้นฉบับก่อนเริ่ม transaction สำหรับ import/batchImport; การตรวจสิทธิ์ สถานะนำเข้า รหัสซ้ำ และการเขียนยังตรวจใน Serializable transaction
- หน้านำเข้าใช้ effect เดียว ยกเลิกคำขอเมื่อเปลี่ยนตัวกรอง/ออกจากหน้า รักษาตารางระหว่าง refresh และปิดปุ่มเขียนระหว่างข้อมูลยังไม่ล่าสุด; ปรับหน้าสุดท้ายเมื่อจำนวนรายการลดลง
- คำขอนำเข้ามี token คงเดิมพร้อม payload เดิมเมื่อ retry หลังเครือข่ายล้มเหลว และรวมการกดซ้ำของงานเดียวกัน; เพิ่ม shared type contract กับการตรวจข้อมูลตอบกลับก่อน render
- ตรวจนับส่ง `expectedCheckedAt` (null สำหรับยังไม่ตรวจ หรือ ISO ล่าสุด) ปฏิเสธฟอร์มเก่า/คำขอชนกัน และเพิ่ม timestamp ทุกครั้งโดยไม่ต้อง migration
- ผล mismatch รับจำนวนพบจริงที่เกินทะเบียนได้ ชื่อ/รหัสในรอบเก่าใช้ snapshot ณ เปิดรอบ
- รูปที่แนบหลังบันทึกข้อมูลไม่สำเร็จมีคำเตือนและปุ่มเปิดรายการเดิมเพื่อแก้ต่อ โดยไม่สร้างครุภัณฑ์ซ้ำ
- ผ่าน unit tests 25 กรณี, domain tests, typecheck, production build และ integration บน PostgreSQL ฐานใหม่แยก รวม stale/concurrent checks, จำนวนเกิน, ประวัติหลังเปลี่ยนชื่อ, การนำเข้า 1,194 แถวตรงทุกสตางค์ และรูปภาพครบสิทธิ์/ขนาด/ไฟล์เสีย/คำขอชนกัน
- ลอง browser บนฐานทดสอบ: กรอกราคา 1,000.00 จำนวน 2 ได้ยอด 2,000.00; สร้างราคา 0 และแก้ชื่อสำเร็จ; รูปเสียแจ้ง partial failure และเปิดรายละเอียดรายการที่บันทึกแล้วได้
- ลองนำเข้า Excel ผ่าน browser บนฐานทดสอบ: แถวที่มีหมายเหตุ “เจ้าหน้าที่พัสดุ” และ “ซื้อรวมเป็นเงิน 500 บาท” แสดงพร้อมนำเข้าครบ 2 รายการ; ยืนยันนำเข้าทั้งหมดแล้วสถิติเป็นนำเข้าแล้ว 2 รอนำเข้า 0 และทุกแถวต้นทางแสดงสถานะถูกต้อง ไม่ได้วัดจำนวน HTTP requests ผ่าน browser เนื่องจากเครื่องมือตรวจหน้าไม่เปิด Performance API

## แก้พฤติกรรมหลังแยกคอมโพเนนต์ — 27 กันยายน 2569

- ฟอร์มรักษาสาขาเดิม รองรับสาขาจากทะเบียน/ต้นฉบับและค่าที่พิมพ์เพิ่ม; ส่งสภาพที่เลือกจริง และคืน readOnly ให้จำนวน/ราคา/ยอดรวมในโหมดแก้ไขตามกฎ Backend
- รูปที่เลือกขณะนำเข้าทีละรายการใช้ id ที่ Backend คืนหลังบันทึก รักษาคำเตือนเมื่ออัปโหลดรูปไม่สำเร็จโดยไม่สร้างรายการซ้ำ
- QR ไม่แสดงหรือพิมพ์ป้ายจากชุดก่อนเมื่อเปลี่ยนรายการ/ปิดหน้าต่าง; ปิดปุ่ม QR เมื่อไม่มีรายการที่มีสิทธิ์สร้างป้าย
- รวม models เป็นสัญญาข้อมูลระหว่าง Backend และ views แก้ roundId, active แบบตัวเลข และ version ของคำขอ; `api<T>()` ยังเป็น type assertion หลังตรวจเบื้องต้น และยังไม่ได้ตรวจโครงสร้าง JSON ภายในทุก field ตอน runtime
- เพิ่ม 6 tests สำหรับฟอร์มและ QR: รวมผ่าน 31/31 พร้อม typecheck และ production build วันที่ 27 กันยายน
- Browser บนฐานทดสอบวันที่ 27 กันยายนยืนยันการบันทึกสาขา/สภาพ และการรักษายอด 0 หลังแก้ไข
- Browser วันที่ 28 กันยายน: เปลี่ยนจาก QR รายการที่ถือครองไปทะเบียนจำหน่ายแล้วไม่มีป้ายเก่าค้างและปุ่ม QR ถูกปิด; นำเข้า Excel ทีละรายการพร้อม PNG สำเร็จ รูปแสดงทั้งตารางและรายละเอียด สาขาที่ไม่มีในตัวเลือกเดิมยังถูกเก็บตรงต้นฉบับ จำนวน 2 × 125.50 ได้ยอด 251.00 และมี audit การเพิ่มรูป

- ยึด `http://localhost:3000` และฐานข้อมูลเดิมจาก root `.env`; คำสั่ง `dev`/`start` ระบุพอร์ต 3000 และ bind loopback ชัดเจน ไม่เลื่อนไปเปิดเว็บอีกพอร์ตเมื่อพอร์ตหลักถูกใช้งาน
- ตรวจ hash แบบอ่านอย่างเดียว: ทั้ง 5 บัญชี `@ksu.ac.th` มีบทบาท/สถานะถูกต้องและรหัสตรงกับที่ผู้ใช้ให้ ไม่เปลี่ยนรหัสหรือ seed บัญชีใหม่
- สำรองฐานข้อมูลหลักด้วย `pg_dump` แบบ custom archive และตรวจรายการใน archive สำเร็จ สำเนาอยู่ใน `backend/.cache/consolidation/primary-before-20260928.dump` ซึ่งไม่ติดตามใน Git
- ตรวจฐานทดสอบบน PostgreSQL เฉพาะกิจ port 55432 พบเฉพาะบัญชี `@example.test` และฐาน foundation ว่าง แล้วลบฐานทดสอบเก่าทั้ง 6 ฐาน ปิด PostgreSQL ชุดนี้ เหลือเว็บที่เปิดใช้งานบน port 3000
- ยกเลิก retained preview (`--keep`) และการเขียนไฟล์รหัสผ่านของ integration runner; การทดสอบที่เขียนข้อมูลเป็นงานชั่วคราว ปิด process และลบฐานของตัวเองเมื่อจบตามปกติ/เกิดข้อผิดพลาด โดยไม่ใช้เว็บหรือฐานข้อมูลหลัก
- เปรียบเทียบจำนวนแถวและ SHA-256 ของข้อมูลทุกตารางก่อน/หลัง: ข้อมูลหลักทั้ง 19 ตารางไม่เปลี่ยน รวมบัญชี สิทธิ์ session และข้อมูลครุภัณฑ์; health ของ port 3000 เป็น ready
- ผ่าน unit/guard tests 34/34, domain tests, typecheck และ diff-check; ไม่เปิดเว็บทดสอบเพิ่มหรือรัน workflow ที่เขียนข้อมูลในรอบนี้ การเรียก workflow โดยตรงถูกห้ามใช้ port 3000 หรือบัญชีนอก `@example.test` ก่อน login
- ข้อจำกัดการเก็บกวาด: ระบบอนุมัติอัตโนมัติปฏิเสธการลบโฟลเดอร์ทดสอบและไฟล์ `backend/.cache/integration/last-run.json` แม้ระบุไฟล์เดียว โดยแจ้งเพียง `blocked by policy` จึงยังมี metadata รหัสเก่าที่ใช้ไม่ได้แล้ว (ฐานบัญชีถูกลบ) และโครง PostgreSQL ที่ปิดอยู่; ไม่ใช้วิธีอื่นเลี่ยงข้อจำกัดเพื่อลบไฟล์

## แก้ฟอร์มจัดการผู้ใช้ — 28 กันยายน 2569

- เปิดฟอร์มเพิ่มผู้ใช้ได้เมื่อไม่มี `modal.user` โดยเริ่มด้วยชื่อ/อีเมลว่าง บทบาทเจ้าหน้าที่ และเปิดใช้งานบัญชี
- อ่านสถานะ `active` แบบ 0/1 ถูกต้อง บัญชีที่ระงับอยู่ยังไม่ถูกเลือกเปิดใช้งานเมื่อแก้ไขข้อมูลอื่น
- เปลี่ยนบทบาทได้ด้วย `defaultValue` และรักษาค่าที่เลือกเมื่อ parent render หรือบันทึกล้มเหลว; form key เดิมล้างค่าตามรายการที่เปิดใหม่
- แสดงและตรวจรหัสผ่าน 12–128 ตัวอักษรตรง Backend: บังคับสำหรับบัญชีใหม่/คำเชิญ และเว้นว่างเพื่อคงรหัสเดิมเมื่อแก้บัญชีที่มีอยู่
- เพิ่ม tests ที่รัน TSX จริงของ Editor, Field และ Pick โดยจำลอง UI/FormData ไม่เรียก API: ครอบคลุมเปิดฟอร์ม ส่งสถานะระงับ เลือกบทบาท รักษาค่าหลัง error และข้อจำกัดรหัสผ่าน รวมผ่าน 38/38 พร้อม typecheck, production build และ diff-check
- ตรวจ browser บน `localhost:3000`: เปิดเพิ่มผู้ใช้ เปลี่ยนบทบาทเป็นหัวหน้าสำนักงาน ตรวจ min/max รหัส แล้วกดยกเลิก ไม่มีการบันทึกบัญชีหรือรหัสใหม่; เปรียบเทียบ hash ของข้อมูล users ก่อน/หลังพบทั้ง 5 บัญชีไม่เปลี่ยน ภาพยืนยันอยู่ใน `backend/.cache/audit/user-form-fixed.png`

## ขอบเขตที่ยังต้องแยกดำเนินการ (คงเดิม)

- ยังไม่ได้แก้สาขาในทะเบียนเดิมอัตโนมัติ ต้องตรวจประวัติการโอนย้าย/การแก้ไขก่อน เพื่อไม่เขียนทับการตัดสินใจของเจ้าหน้าที่
- ฐานข้อมูลเดิมยังต้องวางแผน baseline migrations ก่อนอัปเกรด schema ครั้งถัดไป; การตรวจรอบนี้ไม่ได้แก้ schema ของทะเบียนเดิม
- backend/data มีไฟล์ต้นฉบับที่ถูกติดตามใน Git อยู่ก่อนแล้ว แม้ .gitignore จะระบุไว้ ต้องจัดการนโยบายเผยแพร่และประวัติ Git ต่างหาก โดยเก็บต้นฉบับในเครื่องไว้ครบ
- ยังไม่ได้เผยแพร่ไปยัง hosting และยังไม่ได้ปรับ Word/DrawIO ทุกฉบับให้ตรงกับโค้ดล่าสุด
