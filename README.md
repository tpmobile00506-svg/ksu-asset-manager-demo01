# ระบบบริหารจัดการครุภัณฑ์

ระบบทะเบียนครุภัณฑ์สำหรับคณะวิศวกรรมศาสตร์และเทคโนโลยีอุตสาหกรรม มหาวิทยาลัยกาฬสินธุ์ ใช้ Node.js, Next.js/React, PostgreSQL และ Prisma

## โครงสร้างโครงการ

Source มีสองโฟลเดอร์หลัก ส่วน package.json, package-lock.json, README และไฟล์ตั้งค่าที่จำเป็นอยู่ที่ root

```text
asset-manager/
├── frontend/                  หน้าจอและ Next.js
│   ├── app/                   หน้าเว็บและตัวเชื่อม API ของ Next.js
│   ├── features/              ทะเบียน นำเข้า คำขอ ตรวจนับ รายงาน ผู้ใช้
│   ├── components/            ส่วนประกอบหน้าจอ
│   ├── hooks/                 React hooks
│   ├── services/              ส่งออก Excel และพิมพ์
│   ├── styles/                CSS และใบอนุญาตของ styles ภายนอก
│   ├── public/                favicon และไฟล์สาธารณะ
│   ├── utils/                 ตัวช่วยหน้าจอ
│   ├── next.config.ts
│   ├── postcss.config.mjs
│   └── tsconfig.json
├── backend/                   API ฐานข้อมูล และกฎธุรกิจ
│   ├── auth/                  เข้าสู่ระบบและ session
│   ├── config/                Environment และการตั้งค่า server
│   ├── contracts/             ชนิดข้อมูลและกฎคำนวณร่วมกับ frontend
│   ├── db/                    เชื่อม PostgreSQL ผ่าน Prisma
│   ├── prisma/                Schema, migrations และ seed
│   ├── routes/                API และไฟล์ต้นฉบับ
│   ├── services/              กฎธุรกิจ สิทธิ์ และธุรกรรม
│   ├── imports/               อ่าน Excel ฝั่ง server
│   ├── storage/               จัดเก็บไฟล์ใน PostgreSQL
│   ├── scripts/               คำสั่งดูแลระบบและนำเข้าต้นฉบับ
│   ├── tests/                 ชุดทดสอบ
│   ├── docs/                  รายงานตรวจโค้ด
│   ├── data/                  ต้นฉบับส่วนตัวในเครื่อง ไม่ส่งขึ้น Git
│   └── archive/               สำเนาโค้ดเก่า ไม่ใช้รันระบบปัจจุบัน
├── package.json
├── package-lock.json
└── README.md
```

`frontend/app/api/` เป็นตัวเชื่อมที่ Next.js ต้องใช้ ส่วนการตรวจสิทธิ์และกฎธุรกิจอยู่ใน backend ทั้งสองฝั่งรันบน Node.js ด้วย origin เดียวกัน ไม่ต้องตั้ง API อีกพอร์ตในการใช้งานปกติ

`node_modules/`, `frontend/.next/`, `backend/generated/` และ cache เป็นไฟล์ที่เครื่องมือสร้าง ไม่ใช่โฟลเดอร์ source เพิ่มเติม

ขั้นตอนอัปเกรดฐานข้อมูลเดิมและการทดสอบอัตโนมัติ: [UPGRADE](backend/docs/UPGRADE.md)

รายละเอียด: [Frontend](frontend/README.md) · [Backend](backend/README.md) · [รายงานตรวจการเปลี่ยนแปลง](backend/docs/CHANGE_AUDIT.md)

## รูปครุภัณฑ์

เปิดรายละเอียดรายการจากรูปย่อหรือชื่อครุภัณฑ์ แล้วเลือก **เพิ่มรูปครุภัณฑ์ → เลือกไฟล์ → บันทึกรูป** รองรับ JPEG, PNG และ WebP ไม่เกิน 4 MB จำนวน 1 รูปต่อรายการ เจ้าหน้าที่และ Admin เพิ่ม เปลี่ยน หรือลบรูปได้ ทุกบัญชีที่เข้าสู่ระบบดูรูปได้

รูปย่อแสดงในตารางทะเบียน ส่วนรายละเอียดแสดงภาพเต็มโดยไม่ตัดขอบ ระบบปรับทิศทาง ย่อด้านยาวไม่เกิน 1,600 พิกเซล และเก็บเป็น WebP ในตาราง `stored_files` เดิม จึงใช้ได้กับฐานข้อมูลปัจจุบันโดยไม่เพิ่มตาราง เก็บประวัติการเปลี่ยนรูปโดยไม่เปลี่ยนจำนวน มูลค่า หรือรุ่นข้อมูลที่ใช้อนุมัติครุภัณฑ์ รูปไม่ได้รวมใน Excel เมื่อแบ่งล็อต ระบบคัดลอกรูปของรายการแม่ไปยังรายการใหม่ทั้งสองรายการ

## เริ่มใช้งาน

ต้องมี Node.js 22.13 ขึ้นไป, npm และ PostgreSQL ที่เข้าถึงได้ คำสั่งทั้งหมดรันจาก root ของโครงการ เตรียม environment ใน `.env` หรือระบบจัดการ secrets ของผู้ให้บริการ:

```dotenv
DATABASE_URL=postgresql://USERNAME:PASSWORD@HOST:5432/DATABASE
FRONTEND_ORIGIN=http://localhost:3000
SESSION_COOKIE_SECURE=false
ADMIN_EMAIL=admin@example.test
ADMIN_PASSWORD=REPLACE_WITH_A_NEW_LONG_PASSWORD
ADMIN_NAME=ผู้ดูแลระบบ
```

คัดลอกจาก `.env.example` ได้เลย (`SESSION_COOKIE_SECURE=true` เมื่อใช้ HTTPS จริง)

ค่าข้างต้นเป็นตัวอย่าง ให้ใช้บัญชีและรหัสผ่านของผู้ดูแลจริง ห้ามนำ `.env` ขึ้น Git หรือวางข้อมูลลับในตัวแปร `NEXT_PUBLIC_*` สำหรับ PostgreSQL ระยะไกลให้ใช้การตั้งค่า TLS ตามผู้ให้บริการ

```bash
npm ci
npm run db:generate
npm run db:deploy
npm run db:seed
npm run dev
```

เปิด [http://localhost:3000](http://localhost:3000) แล้วเข้าสู่ระบบด้วยบัญชี Admin ที่สร้างผ่าน `db:seed` จากนั้นเพิ่มผู้ใช้และบทบาทในระบบ บัญชีผู้ดูแลเริ่มต้นสร้างด้วยคำสั่งที่ระบุชัดเจน ไม่สร้างจากผู้ที่เปิดหน้า login เป็นคนแรก

ใช้ `http://localhost:3000` เป็นเว็บใช้งานชุดเดียว (ใช้ `localhost` ตามที่ตั้งใน `FRONTEND_ORIGIN`) คำสั่ง `dev` และ `start` ระบุพอร์ต 3000 แน่นอน ห้ามเปลี่ยนพอร์ต เพราะการตรวจ Origin และคุกกี้อ้างอิงพอร์ตนี้ หากพอร์ตถูกใช้อยู่ให้หยุด process เดิมก่อน บัญชีผู้ใช้อื่น (เจ้าหน้าที่ หัวหน้า รองคณบดี คณบดี) ให้ Admin สร้างในหน้า "ผู้ใช้งานและสิทธิ์" หลังเข้าสู่ระบบ

`db:generate` สร้าง Prisma Client; `db:deploy` ติดตั้ง migrations; `db:seed` เตรียมบัญชีผู้ดูแล หากนำฐานข้อมูลจากระบบก่อนหน้ามาใช้ ต้องตรวจประวัติ migrations และทำ baseline ให้ตรง schema ก่อน

## ข้อมูลต้นฉบับ

ไฟล์ Excel จริงและข้อมูลที่แปลงจากต้นฉบับเก็บไว้ใน `backend/data/` ภายในเครื่อง และไม่รวมใน repository สาธารณะ NEWPJ02 ใช้คำสั่งนี้เมื่อต้องการนำต้นฉบับที่เตรียมไว้เข้าสู่ PostgreSQL:

```bash
npm run source:seed
```

ไฟล์ที่นำเข้าจากหน้าเว็บเก็บในตาราง `StoredFile` ของ PostgreSQL พร้อมไฟล์ต้นฉบับและข้อมูลสำหรับตรวจทาน ไม่อาศัยดิสก์ชั่วคราวของ Vercel การนำไฟล์เข้าสู่หน้าตรวจทานยังไม่เพิ่มครุภัณฑ์ลงทะเบียนจนกว่าเจ้าหน้าที่ตรวจและยืนยัน

ต้นฉบับ Word/Excel ที่ผู้ใช้ให้ต้องเก็บสำรองไว้ การจัดโฟลเดอร์และการเผยแพร่โค้ดไม่ใช่คำสั่งลบข้อมูลต้นฉบับ

## การทำงานหลัก

- ทะเบียนและไฟล์ส่งออก 10 คอลัมน์ (รวมสถานที่ในหมายเหตุ) ค้นหา กรอง เรียงลำดับ และพิมพ์ QR; การอ่านต้นฉบับรองรับรูปแบบ 11 คอลัมน์ที่แยกสถานที่ด้วย
- ตรวจทาน Excel แยกหัวกระดาษ เลขหน้า ยอดยก และหัวชุดออกจากยอดทะเบียน โดยเก็บต้นฉบับไว้
- แยกรหัสช่วงที่แน่นอนเป็นครุภัณฑ์และ QR อิสระ แบ่งล็อตโดยยอดจำนวนและเงินยังเท่าเดิม
- ส่งคำขอโอนย้าย ซ่อม จำหน่าย และอนุมัติตามลำดับ พร้อมประวัติ ถ้าคำขอระบุจำนวนเพียงบางส่วน ระบบจะ **แบ่งล็อตเมื่ออนุมัติขั้นสุดท้าย** ไม่ใช่ตอนยื่นคำขอ (ถูกส่งกลับ = ทะเบียนไม่เปลี่ยน)
- URL จำหน้าที่เปิดอยู่ (`/?view=requests` ฯลฯ) ใช้ปุ่ม Back และรีเฟรชได้
- ตรวจนับประจำปีและรายงานมูลค่า ประมาณค่าเสื่อมเมื่อข้อมูลวันที่รับและอายุใช้งานครบ
- ผู้ใช้ 5 กลุ่ม: เจ้าหน้าที่ หัวหน้าสำนักงาน รองฝ่ายบริการ คณบดี และ Admin

สายอนุมัติเริ่มต้นคือ หัวหน้าสำนักงาน → รองฝ่ายบริการ → คณบดี ผู้ดูแลปรับสายอนุมัติได้ ส่วนคำขอที่ส่งแล้วเก็บสายอนุมัติ ณ วันที่ส่ง Admin จัดการบัญชีและทะเบียน แต่ไม่อนุมัติแทนผู้บริหาร

จำนวนเงินในฐานข้อมูลเก็บเป็นจำนวนเต็มหน่วยสตางค์ (`BigInt`) และแปลงเป็นตัวเลขที่ปลอดภัยก่อนส่ง JSON ตัวอย่าง 400 ตัว รวม 370,000 บาท แบ่งชำรุด 189 ตัวเป็น 174,825 บาท และปกติ 211 ตัวเป็น 195,175 บาท รายการแม่ของการแบ่งล็อตเก็บเป็นประวัติเพื่อไม่ให้นับเงินซ้ำ

## การเผยแพร่และ Deploy ขึ้น Production (Vercel + Neon PostgreSQL)

ระบบรองรับการ Deploy ขึ้น Cloud แบบ Serverless ผ่าน **Vercel** ร่วมกับฐานข้อมูลคลาวด์ **Neon PostgreSQL** ได้อย่างสมบูรณ์แบบ

### 1. การเตรียมฐานข้อมูล (Neon PostgreSQL)
1. สร้างโปรเจกต์ PostgreSQL บน [Neon Console](https://console.neon.tech)
2. คัดลอก Connection String (แนะนำแบบ Pooler connection):
   ```text
   DATABASE_URL="postgresql://neondb_owner:PASSWORD@ep-....ap-southeast-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require"
   ```
3. รัน Migration และสร้างบัญชี Admin เริ่มต้น:
   ```bash
   npx prisma migrate deploy --schema backend/prisma/schema.prisma
   npm run db:seed
   ```

### 2. การตั้งค่าบน Vercel (Project Settings)
1. **Import Repository**: เลือก repository ของโครงการนี้บน GitHub
2. **Root Directory**: ให้คงค่าเป็น **`./`** (สำคัญมาก: ห้ามเปลี่ยนเป็น `frontend` เนื่องจากโครงสร้างโปรเจกต์มีโฟลเดอร์ `backend/prisma/` อยู่ร่วมที่ root)
3. **Framework Preset**: เลือก **Next.js**
4. **Build & Output Settings**:
   - **Build Command**: ค่าเริ่มต้น `npm run build` (ครอบคลุม `prisma generate` และ `next build frontend`)
   - **Output Directory**: กำหนดเป็น `frontend/.next` (มีไฟล์ `vercel.json` คุมไว้แล้ว หรือตั้งเปิด Override เป็น `frontend/.next`)

### 3. การกำหนด Environment Variables บน Vercel
กำหนดตัวแปร 6 ตัวต่อไปนี้ในหน้า **Project Settings → Environment Variables** (สำหรับทั้ง Production และ Preview):

| ชื่อตัวแปร (Key) | ตัวอย่างค่า (Value) | คำอธิบาย |
| :--- | :--- | :--- |
| `DATABASE_URL` | `postgresql://...neon.tech/neondb?sslmode=require...` | Connection String ไปยัง Neon PostgreSQL |
| `FRONTEND_ORIGIN` | `https://YOUR-PROJECT.vercel.app` | URL โดเมนของระบบที่รันบน Vercel (ต้องตรงกับโดเมนจริง) |
| `SESSION_COOKIE_SECURE` | `true` | เปิดใช้งาน Secure Cookie บน HTTPS สำหรับ Production |
| `ADMIN_EMAIL` | `admin@example.test` | อีเมลของบัญชีผู้ดูแลระบบหลัก (ใช้อีเมลจริงของผู้ดูแล) |
| `ADMIN_PASSWORD` | `<ตั้งรหัสผ่านใหม่ที่ยาวและเดายาก>` | รหัสผ่านผู้ดูแลระบบ (ความยาว 12–128 ตัวอักษร) ห้ามใช้ค่าตัวอย่าง |
| `ADMIN_NAME` | `ผู้ดูแลระบบ (Admin)` | ชื่อที่แสดงของผู้ดูแลระบบ |

### 4. การสั่ง Deploy
- ไปที่แท็บ **Deployments** บน Vercel
- คลิกเมนู `...` หรือกด **Create Deployment**
- ระบุ Branch: **`main`** แล้วกดยืนยันเพื่อเริ่มกระบวนการ Deploy
- เมื่อ Build สำเร็จ สถานะจะขึ้นเป็น **Ready** และสามารถเข้าใช้งานผ่านโดเมนของ Vercel ได้ทันที

### 5. การตรวจสอบความเรียบร้อยก่อนส่งมอบ (Smoke Test)
1. เปิดหน้าเว็บตาม URL ที่ Vercel สร้างให้
2. เข้าสู่ระบบด้วยอีเมลและรหัสผ่านของผู้ดูแลระบบ (`ADMIN_EMAIL` / `ADMIN_PASSWORD`)
3. ตรวจสอบแท็บทะเบียนครุภัณฑ์, การค้นหา, ตัวกรอง, การแบ่งล็อต, การจัดการสิทธิ์ผู้ใช้ และการออกรายงาน Excel/พิมพ์ QR Label



## งานที่ยังค้าง (สำหรับผู้รับช่วงต่อ)

รายละเอียดและกฎการทำงานอยู่ใน `CLAUDE.md` หัวข้อ 6–7 สรุปคือ: รอยืนยันกฎมูลค่าซาก/การนับเวลาค่าเสื่อมและค่าเริ่มต้นปีงบประมาณจากอาจารย์ที่ปรึกษา, `getData()` โหลดครุภัณฑ์ทั้งหมดในครั้งเดียว (ควรทำ pagination เมื่อข้อมูลโต), ไฟล์หน้าจอขนาดใหญ่ (`workspace.tsx`, `audit-view.tsx`) ควรแยกส่วน และก่อนแก้ `schema.prisma` ต้องสำรองฐานข้อมูลก่อนเสมอ (ห้าม `prisma migrate reset` และ `db push` กับฐานข้อมูลจริง)

## ทดสอบการแก้ไข

```bash
npm test
npm run test:domain
npm run typecheck
npm run build
```

`npm run test:integration` เป็นการทดสอบอัตโนมัติที่เขียนข้อมูล จึงต้องกำหนด `ASSET_TEST_DATABASE_URL` เป็น PostgreSQL ในเครื่องสำหรับทดสอบเท่านั้น ตัว runner สร้างข้อมูลชั่วคราว ทดสอบ API แล้วปิด process และลบฐานข้อมูลที่สร้างเอง ไม่เก็บเว็บหรือไฟล์รหัสไว้ใช้งานต่อ และไม่รองรับ `--keep` การตรวจหน้าเว็บตามปกติให้ใช้ `http://localhost:3000` กับบัญชีเดิม ห้ามนำชุดทดสอบที่สร้าง/แก้ไข/ลบข้อมูลไปรันกับฐานข้อมูลหลัก อ่านรายละเอียดใน UPGRADE.md

หน้า login ใช้บัญชีที่ Admin สร้าง ไม่มีบัญชีหรือรหัสผ่านกรอกล่วงหน้า การแก้ไขชื่อห้อง/สาขาที่บันทึกผิดทำได้พร้อมเหตุผลและ audit ส่วนการโอนย้ายจริงใช้คำขอและสายอนุมัติ
